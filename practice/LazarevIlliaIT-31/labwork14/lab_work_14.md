Завдання 1. Атомарна пара INSERT + UPDATE

У межах однієї транзакції додано новий продаж місячного абонемента клієнту з `id = 1` та продовжено дату завершення попереднього продажу цього самого клієнта.

```sql
BEGIN;

INSERT INTO membership_sales
    (id, membership_id, client_id, purchase_date, expiration_date)
VALUES (11, 3, 1, '2026-10-10', '2026-11-09');

UPDATE membership_sales
SET expiration_date = '2026-10-10'
WHERE id = 9 AND client_id = 1;

COMMIT;
```

Перевірка після виконання:
```sql
SELECT id, membership_id, client_id, purchase_date, expiration_date
FROM membership_sales
WHERE id IN (9, 11)
ORDER BY id;
```

Результат:
- Попередній продаж `id = 9` має дату завершення `2026-10-10`.
- Новий продаж `id = 11` має дату придбання `2026-10-10` і дату завершення `2026-11-09`.

**Чому зміни мають виконуватися разом?**

Новий продаж абонемента та продовження попереднього періоду обслуговування є однією логічною операцією. Якби між `INSERT` і `UPDATE` стався збій, у базі міг би з'явитися новий продаж без відповідного оновлення попереднього запису. Транзакція дозволяє зафіксувати обидві зміни разом або скасувати їх разом.

Завдання 2. Свідомий ROLLBACK

Було відкрито транзакцію, додано тестовий продаж з `id = 12`, перевірено його наявність, після чого виконано `ROLLBACK`.

```sql
BEGIN;

INSERT INTO membership_sales
    (id, membership_id, client_id, purchase_date, expiration_date)
VALUES (12, 2, 2, '2026-10-11', '2026-10-18');

SELECT COUNT(*) FROM membership_sales WHERE id = 12;

ROLLBACK;

SELECT COUNT(*) FROM membership_sales WHERE id = 12;
```

Результат: до `ROLLBACK` запит повернув `1`, після `ROLLBACK` — `0`. Отже, доданий тестовий запис було повністю скасовано.

Завдання 3. Проміжний стан усередині транзакції

```sql
BEGIN;

UPDATE membership_sales
SET expiration_date = '2026-10-20'
WHERE id = 10;

SELECT id, expiration_date
FROM membership_sales
WHERE id = 10;

ROLLBACK;
```

**Чи видно власну зміну до COMMIT?**

Так. У тій самій сесії SQLite бачить власні зміни одразу після виконання команди `UPDATE`, навіть якщо транзакцію ще не зафіксовано. У проміжному `SELECT` було видно дату `2026-10-20`.

Це не означає, що зміна вже стала остаточною. До `COMMIT` її можна скасувати командою `ROLLBACK`. Після відкату для запису `id = 10` відновилася попередня дата `2026-12-09`.

Завдання 4. Свідома помилка всередині транзакції

У транзакції спочатку було успішно додано продаж з `id = 12`. Далі виконано спробу додати клієнта з електронною поштою, яка вже існує в таблиці `clients`.

Команда, що спричиняє помилку:
```sql
INSERT INTO clients (id, first_name, last_name, email, phone)
VALUES (5, 'Тест', 'Дубль', 'ivan.petrenko@example.com', '+380000000000');
```

**Точний текст помилки SQLite:**
```text
UNIQUE constraint failed: clients.email
```

Після помилки перевірено перший успішний `INSERT`:
```sql
SELECT id, membership_id, client_id, purchase_date, expiration_date
FROM membership_sales
WHERE id = 12;
```

Результат: запис з `id = 12` був видимий у тій самій відкритій транзакції. Це доводить, що помилка другого SQL-оператора не скасувала автоматично першу успішну зміну.

Після перевірки виконано `ROLLBACK`. Контрольний `SELECT COUNT(*)` повернув `0`, тобто перший запис також було скасовано.

Завдання 5. Забутий ROLLBACK

Сценарій повторено: спочатку успішно додано продаж з `id = 13`, потім виконано команду з дубльованою електронною поштою.

Точний текст помилки SQLite:
```text
UNIQUE constraint failed: clients.email
```

Цього разу замість `ROLLBACK` виконано `COMMIT`.

Перевірка:
```sql
SELECT id, membership_id, client_id, purchase_date, expiration_date
FROM membership_sales
WHERE id = 13;

SELECT COUNT(*) FROM clients;
```

**Результат:** продаж з `id = 13` залишився в таблиці, а кількість клієнтів залишилася `4`. Тобто перша успішна зміна була зафіксована, а друга, помилкова команда не додала клієнта.

**Чому так сталося?**

За типової поведінки SQLite `ABORT` скасовує саме невдалу SQL-команду, а не всю транзакцію. Транзакція при цьому залишається відкритою. Тому наступний `COMMIT` фіксує всі попередні успішні команди цієї транзакції.

Це небезпечно для розробника, який помилково вважає, що будь-яка помилка автоматично скасовує всю транзакцію. Щоб скасувати всі попередні зміни після помилки, потрібно явно виконати `ROLLBACK`.

### Контрольні питання

**1. Що пішло б не так у завданні 1, якби INSERT та UPDATE були окремими?**

Якби між командами стався збій, у базі міг би залишитися новий продаж без оновлення попереднього запису. Це створило б неузгодженість даних. Транзакція забезпечує спільну фіксацію обох операцій.

**2. Чому після COMMIT у завданні 5 збереглася лише перша зміна?**

Тому що перший `INSERT` завершився успішно, а другий оператор порушив обмеження `UNIQUE`. SQLite скасувала невдалий оператор, але залишила транзакцію відкритою. Команда `COMMIT` зафіксувала попередній успішний `INSERT`.

**3. Чому це не суперечить принципу атомарності?**

SQLite гарантує атомарне виконання транзакції під час її фіксації або відкату. Але помилка окремого оператора з конфліктною поведінкою `ABORT` не означає автоматичного відкату всієї транзакції. Розробник повинен самостійно виконати `ROLLBACK`, якщо хоче скасувати всі зміни транзакції.

Висновок

Під час практичної роботи було виконано атомарну пару `INSERT` та `UPDATE`, перевірено повне скасування змін за допомогою `ROLLBACK`, досліджено видимість власних змін до `COMMIT` та поведінку SQLite у разі порушення обмеження `UNIQUE`. На практиці підтверджено, що помилка одного оператора не обов'язково скасовує всю транзакцію. Якщо після такої помилки виконати `COMMIT`, попередні успішні зміни можуть бути збережені. Тому для забезпечення цілісності даних розробник має правильно керувати транзакціями.
