Завдання 1. План запиту до індексу
Виконано запит:

```sql
EXPLAIN QUERY PLAN
SELECT * FROM membership_sales
WHERE client_id = 1;
```

План до створення індексу:

```text
2 | 0 | 0 | SCAN membership_sales
```

SQLite переглядає таблицю `membership_sales` (операція `SCAN`), оскільки окремого індексу для пошуку за `client_id` ще немає.

Завдання 2. Індекс на зовнішньому ключі
Створено індекс:

```sql
CREATE INDEX idx_sales_client
ON membership_sales(client_id);
```

План після створення індексу:

```text
3 | 0 | 0 | SEARCH membership_sales USING INDEX idx_sales_client (client_id=?)
```

План змінився з повного перегляду таблиці на пошук через індекс (`SEARCH ... USING INDEX`). Індекс дає змогу швидше знаходити продажі абонементів конкретного клієнта, особливо коли таблиця містить багато записів.

Завдання 3. Композитний індекс
Перевірено запит із двома умовами:

```sql
SELECT * FROM membership_sales
WHERE client_id = 1 AND membership_id = 3;
```

План до композитного індексу:

```text
3 | 0 | 0 | SEARCH membership_sales USING INDEX idx_sales_client (client_id=?)
```

Створено композитний індекс:

```sql
CREATE INDEX idx_sales_client_membership
ON membership_sales(client_id, membership_id);
```

План після створення:

```text
3 | 0 | 0 | SEARCH membership_sales USING INDEX idx_sales_client_membership (client_id=? AND membership_id=?)
```

Композитний індекс охоплює одразу дві колонки, тому SQLite може використовувати їх разом для пошуку. Індекс лише за першою колонкою теж може допомогти, але композитний індекс краще відповідає запиту, який одночасно фільтрує за `client_id` та `membership_id`.

Завдання 4. Індекс і ORDER BY
Перевірено сортування за датою покупки:

```sql
SELECT * FROM membership_sales
ORDER BY purchase_date;
```

План до індексу:

```text
3 | 0 | 0 | SCAN membership_sales
13 | 0 | 0 | USE TEMP B-TREE FOR ORDER BY
```

Створено індекс:

```sql
CREATE INDEX idx_sales_purchase_date
ON membership_sales(purchase_date);
```

План після індексу:

```text
4 | 0 | 0 | SCAN membership_sales USING INDEX idx_sales_purchase_date
```

Після створення індексу SQLite може читати записи в порядку значень `purchase_date`. У плані зникає окремий крок сортування `USE TEMP B-TREE FOR ORDER BY`, якщо оптимізатор використовує індекс для цього запиту.

Завдання 5. Видалення індексу
Видалено індекс дати:

```sql
DROP INDEX idx_sales_purchase_date;
```

План після видалення:

```text
3 | 0 | 0 | SCAN membership_sales
13 | 0 | 0 | USE TEMP B-TREE FOR ORDER BY
```

Після видалення індексу SQLite знову виконує повний перегляд таблиці та використовує тимчасову B-tree структуру для сортування. Перевірка через `sqlite_master`:

```sql
SELECT name
FROM sqlite_master
WHERE type = 'index'
  AND name = 'idx_sales_purchase_date';
```

Запит повернув **0 рядків**, отже індекс успішно видалено.

Контрольні питання

**1. Чому EXPLAIN QUERY PLAN показує план, а не результат запиту?**  
Ця команда пояснює, як SQLite збирається виконати запит: чи буде переглядати всю таблицю, використовувати індекс або виконувати додаткове сортування. Вона не повертає самі записи. План допомагає оцінити спосіб виконання запиту, а не лише перевірити, чи він працює.

**2. Чому композитний індекс ефективніший за індекс лише на першій колонці?**  
Тому що композитний індекс містить значення обох колонок і може врахувати обидві умови фільтрації. Одноколонковий індекс допомагає знайти записи за першою колонкою, але для другої умови може знадобитися додаткова перевірка.

**3. Яка ціна створення індексу?**  
Індекс займає додаткове місце на диску. Під час `INSERT`, `UPDATE` і `DELETE` SQLite також має оновлювати індекси, що додає витрати часу. Тому не потрібно індексувати всі колонки без потреби: індекси варто створювати для колонок, які часто використовуються у фільтрації, з'єднанні таблиць або сортуванні.

### Висновок
Під час практичної роботи створено одноколонковий і композитний індекси, перевірено їхній вплив на плани виконання запитів за допомогою `EXPLAIN QUERY PLAN`. Також досліджено сортування за датою покупки та видалення індексу командою `DROP INDEX`. Робота показала, що індекси можуть зменшувати обсяг перегляду даних і прискорювати пошук та сортування, але потребують додаткового місця й обслуговування.
